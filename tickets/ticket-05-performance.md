# Decision Ticket 5: 性能与架构策略

## Question

global 视角 + 实时更新 + 大量 fiber 时的性能和架构策略？

### 背景
DSH 进程可能有数百个 fiber（多个 session × 多个插件）。当前轮询方案（每秒 ping）可能不够实时或太耗资源。

### 选项分析

**数据推送策略**：

| 方案 | 实时性 | 复杂度 | 适用场景 |
|-----|:---:|:---:|:---|
| 轮询（当前） | 低 | 低 | 简单场景 |
| 长轮询 | 中 | 中 | 兼容性好 |
| Server-Sent Events | 高 | 中 | 单向推送 |
| WebSocket | 高 | 高 | 双向通信 |
| 事件驱动（Host→Client） | 最高 | 高 | 最理想 |

**渲染优化**：

1. **虚拟化**：只渲染视口内的节点
2. **分层渲染**：结构层（静态）+ 活动层（动态）分离
3. **增量更新**：只更新变化的节点
4. **Web Worker**：复杂计算 offload

### 需要决定

1. 数据推送机制（保持轮询？还是升级？）
2. 渲染架构（Canvas vs SVG vs DOM）
3. 更新频率（实时 vs 节流）
4. 内存管理（大量历史数据？）

## 建议下一步

Grilling：与用户讨论性能需求和约束。
